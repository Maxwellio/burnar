## 1. Открытие (Delphi → веб)

В Delphi кнопка «Открыть» и даблклик по гриду кладут `CodNar` в `frmMain.keynar` и вызывают `OpenNar`. Тот открывает `TfrmComNarZad` и/или `TfrmComNarVip`, если `qrCountDefNarZad` / `qrCountDefNarVip` вернул 1 (есть строка в `defnarzad` / `defnarvip`).

В вебе:

| UI | Поведение |
|----|-----------|
| Кнопка «Открыть» | `disabled`, пока нет `selectedId`; `navigate('/naryad/' + id)` |
| Двойной клик по строке | тот же `handleOpen`; `BaseTable` передаёт `row.original.id` |
| «Удалить» | `disabled` без выбранной строки; обработчика пока нет |

`id` = `defnar.key` = `NaryadListDto.id` / `codNar`. Список на главной по умолчанию идёт по этому коду по возрастанию.

Маршрут: `/naryad/:id`. Прямой URL в монолите отдаёт SPA через `SpaForwardController` (`/naryad`, `/naryad/**`).
Заголовок карточки: `GET /api/naryady/{id}` → `{ id, nameNar, hasZadanie, hasVipolnenie, zadanieClosed, vipolnenieClosed }` (тот же ACL, что у списка; 404 если нет доступа). Флаги закрытия nullable и управляют действиями только своей части.

Стартовые вкладки (`initialOpenPanels`):

| `hasZadanie` | `hasVipolnenie` | Открыто |
|--------------|-----------------|---------|
| true | true | Задание + Выполнение |
| true | false | только Задание |
| false | true | только Выполнение |
| false | false | Задание (страница не пустая) |

Пока `hasVipolnenie` ложно, кнопка «Выполнение» неактивна. Повторный клик по единственному заданию на неё не переключается. После `vipolnenie_create` кнопка становится активной и вкладка выполнения открывается рядом с заданием.

## 2. Страница карточки

`frontend/src/features/naryad/NaryadPage.jsx` — action bar под шапкой приложения:

| Элемент | Поведение |
|---------|-----------|
| `ToggleButtonGroup` «Задание» / «Выполнение» | **не exclusive**: обе могут быть включены; снять последнюю нельзя. «Выполнение» неактивно, пока нет `defnarvip` |
| Подпись | `Наряд - {id} {nameNar}` из `GET /api/naryady/{id}` |
| Справа | заглушка общих параметров; **«Каталог»** открывает read-only дерево тематических разделов (раскрытие и фильтры помнятся, пока открыта карточка); **«Выйти из наряда»** (`Close`) → `navigate('/')` |

Пункт меню «Наряды» остаётся активным на `/naryad/:id`.

Рабочая область: при одной вкладке — 100%; при обеих — две колонки 50/50 (задание слева, выполнение справа), без drag-сплиттера между вкладками. Выключенная вкладка скрывается через `display: none` и **не размонтируется**, чтобы ширины колонок сохранились.

Ресайз колонок изолирован: у задания и выполнения свои массивы колонок (уникальные `id`) и свои экземпляры `BaseTreeTable` / `BaseTable`. Раньше один workspace подменял `columns` — ширины «уезжали» на соседней вкладке.

Под каждым деревом `NaryadWorkspacePanel` рисует неподвижную строку состояния.
Итоги видны всегда, даже без выбора. Одна строка показывает `Код: {id}`, несколько —
`Выбрано: N`, и этот текст стоит перед итогами. Задание: «Общая продолжительность».
Выполнение: «Общая нормативная продолжительность» и «Общая фактическая продолжительность».
Между соседними кусками — вертикальная черта на всю высоту полосы. Один кусок рисуется без черты.
Числа — сумма листьев всего дерева (`GET .../totals`), в часах, как `CalcItogsNS`:
строка с детьми своей нормой в сумму не входит. Ячейки родителей в таблице не переписываются.
Параметры и алгоритм читают строку только когда выбрана ровно одна; при нескольких
выбранных правая панель пустая. Общий `BaseTreeTable` не содержит прикладного футера
и прокручивается независимо. Если подписи не помещаются, полоса прокручивается по горизонтали.

### Вкладка «Задание»

`NaryadWorkspacePanel` с `part={zadaniePart}`:

| Элемент | Поведение |
|---------|-----------|
| Action bar задания (48px) | сквозные параметры, создать пустое выполнение, удалить помеченные работы, удалить блок без вложенных, закрыть/открыть, расчёт нормы, затем цвет выбранных строк |
| Слева | `BaseTreeTable` `GET /api/naryady/{id}/zadanie` (корни, свёрнуто); дети — `GET .../zadanie/{nodeId}/children` |
| Справа сверху | `BaseTable` `GET /api/naryady/{id}/zadanie/params?nodeId=` — массив; пусто без выбора или если тип не 79/80 |
| Справа снизу ~120px | read-only поле алгоритма: `GET .../zadanie/algorithm?nodeId=` (`algs.ops`, только тип 80) |

Ширина правой панели тянется сплиттером и пишется в `localStorage` отдельно для задания и выполнения (`naryad-right-panel-width:zad` / `:vip`; старый общий ключ читается как fallback). В storage уходит только значение после drag; ResizeObserver только поджимает отображение, чтобы сплит 50/50 не затирал сохранённую ширину. По умолчанию 25%, min 180px, max 50%.

Ширины колонок дерева и параметров пакет кладёт в `table-column-sizing:${url}` (url с id наряда). Перед монтированием таблицы мы копируем туда стабильные ключи `naryad-column-sizing:zadanie-tree` / `zadanie-params` / `vipolnenie-tree` / `vipolnenie-params`, после ресайза копируем обратно — раскладка общая для всех нарядов.

Колонки дерева (видимые Delphi `trGrdNar`): Код, № п/п, Название работы (expander), Время начала, Источник норм., группа «Интервал» (от, до), группа «Норма времени» (Н.в. на ед., Н.в. на объём). «ЭКС» закомментирован. Одиночные колонки шапки тянутся на оба ряда. Фильтров колонок нет.

Колонки параметров (Delphi `GrdParams`): Параметр (`nm`), Значение (`val`). Значение непрерывного параметра вводится в ячейке, дискретного — выбирается из списка. Дата начала: `dd.mm.yyyy` или `dd.mm.yyyy HH:mm`, если есть часы и минуты.

Отдельный экземпляр `NaryadWorkspacePanel` с `part={vipolneniePart}`:

| Элемент | Поведение |

## 3. Пустое выполнение, импорт и замена

«Создать пустое наряд-выполнение» стоит на панели задания и повторяет `actCreateCopyNarVip`. Кнопка активна, когда задание закрыто, в нём есть корневая работа (`hasRoots` в итогах) и строки `defnarvip` ещё нет. Подтверждения нет. `POST /api/naryady/{id}/vipolnenie` вызывает `burnar.vipolnenie_create`. Повторный вызов сервер отвергает: процедура удалила бы уже созданные работы. Успех возвращает заголовок карточки, включает вкладку выполнения и открывает её рядом с заданием.

«Импортировать работы из задания» стоит на панели выполнения и повторяет `actImportRabZad`. Кнопка активна, когда выполнение открыто, список блокировок уже загружен и в нём нет ни одной работы. Вопрос: «Все существующие работы в выполнении будут удалены, Вы уверены?». `POST .../vipolnenie/import-zadanie` вызывает `burnar.zadanie_to_vipolnenie` с пустой датой. Закрытая часть, любая работа и заблокированная работа дают отказ до вызова. После вызова дерево перечитывается и при успехе, и при отказе: процедура может записать работы и затем сообщить «Операции, не входящие в блоки не были перенесены!». Пустая `defnarvip.begdate` приходит текстом процедуры «Дата начала выполнения работ не задана!».

«Заменить задание на выполнение» повторяет `ToolButton23`. В `FormCreate` видимость завязана на `frmMain.Org` карьеры (`1` или `8`), но обработчик клика и `burnar.copy_vip_to_zad` орг. единицу не проверяют. В работающем Delphi кнопкой пользуются и админ, и обычный пользователь. В вебе она видна всем, кто открыл карточку: у веб-админа часто нет активной карьеры, и проверка org его прячет. Закрытие выполнения кнопку не гасит. Вопрос: «Наряд-задание будет заменено на наряд-выполнение, Вы уверены, что хотите продолжить?». `POST .../vipolnenie/replace-zadanie` вызывает `burnar.copy_vip_to_zad`. Успех — «Изменения успешно сохранены!», дерево задания перечитывается, флаг закрытия задания берётся из заголовка. Дерево выполнения не перечитывается.

## 4. Закрытие и блокировка

На панели задания и выполнения одна кнопка. У открытой части подпись «Закрыть задание от изменения» или «Закрыть выполнение от изменения», у закрытой — «Открыть наряд».

Закрытие задания спрашивает подтверждение и вызывает `burnar.zadanie_closenar`. Отказ процедуры показывается диалогом, дерево после этого перечитывается: даты могли измениться. Закрытие выполнения требует, чтобы в `vipolnenie_oper` не осталось строк с `locked = 0`, иначе «Не все работы заблокированы!». Успех — «Изменения успешно сохранены!». Открытие без вопроса ставит `closed = 0` и сразу обновляет флаг карточки.

Блокировка и разблокировка есть только у выполнения и недоступны у закрытой части.

Триггеры журналов (`ftrg_defnar*_upd` → `log_nar`, `ftrg_log_atrib_*` → `log_atrib` и др.)
читают `current_setting('burnar.user_id')`, `USERENV.OS_USER` и `USERENV.HOST`. Delphi ставил их
при входе. В вебе `DbSessionDataSource` при каждой выдаче соединения из пула сначала делает
`RESET` всех трёх (возврат к умолчаниям базы), а для вошедшего пользователя ставит
`set_config(..., false)`: логин, адрес клиента (первый `X-Forwarded-For` или адрес соединения)
и `burnar.users.users_id` по логину. Уровень сессии, а не транзакции: процедуры с `COMMIT`
вызываются при autocommit. Если запись не удалась, соединение всё равно выдаётся, журнал
получит умолчания базы.

| Выделение | Кнопки |
|-----------|--------|
| только `locked = 1` | разблокировка |
| только открытые | блокировка |
| и те, и другие | обе |

Признаки блокировки всех работ приходят один раз вместе с загрузкой дерева: `GET .../vipolnenie/lock-flags`. Выбор строки этот список не запрашивает заново. Таблицу для этого менять не нужно. Сервер сам упорядочивает выбранные id обходом «родитель, затем дети по prnum». Блокировка — один `vipolnenie_lock_oper` по самой поздней. Разблокировка — один `vipolnenie_un_lock_oper` по самой ранней. Невыделенные строки внутри этого диапазона тоже меняются. Если самая поздняя уже заблокирована, процедура не вызывается. После вызова дерево перечитывается с корней, а уже раскрытые узлы запрашивают детей заново. Это делает `BaseTreeTable` из `mainComponent-changes`: пока файл не перенесён в пакет, после перечитывания видны только корни.

## 5. Цветовая маркировка строк

У задания и выполнения отдельные пары кнопок «Выделить строку цветом» /
«Сбросить цвет» на собственных внутренних action bar. Обе кнопки недоступны,
пока не выбрана ни одна строка, и при `closed === true` у соответствующей части.
Обычный клик выбирает одну строку. `Ctrl` или `Cmd` добавляет либо снимает
строку, `Shift` выделяет непрерывный диапазон видимых раскрытых строк, а
`Ctrl+Shift` добавляет такой диапазон к текущему набору. Свёрнутые узлы в
диапазон не входят. Цвет и сброс записываются во все выбранные строки одним
запросом; потомки сами не красятся.

«Выделить строку цветом» открывает палитру готовых образцов. Пункт «Свой цвет»
— это видимое поле `input type="color"` на всю строку: и надпись, и образец
нажимает сам пользователь. Поле не обрезается, не делается прозрачным и не
открывается скриптом: иначе Chrome прячет курсор внутри системного селектора.
Подсказка иконки гаснет в момент клика и не появляется снова, пока указатель
заново не войдёт на иконку. Палитра остаётся открытой,
пока селектор открыт. Промежуточный оттенок сразу рисуется на выбранных строках и
сохраняется запросом, не дожидаясь закрытия селектора. Третья строка палитры
показывает до пяти последних цветов, подтверждённых закрытием селектора
«Свой цвет». Промежуточные оттенки и чёрный туда не записываются. Список общий
для задания и выполнения, лежит в `localStorage` под ключом
`naryad-recent-row-colors` и читается при открытии палитры. Клик по такой
клетке красит строку как готовый образец и порядок списка не меняет.
CSS `#RRGGBB` перед отправкой
преобразуется в совместимое с Delphi BGR-число, а `colorsel` из первоначально и
лениво загруженных узлов преобразуется обратно. Значение `0` означает отсутствие
фона, поэтому чёрный цвет имеет то же действие, что и сброс, и не может быть
сохранён как чёрная маркировка.

Одна строка по-прежнему может уйти через
`PATCH /api/naryady/{id}/{zadanie|vipolnenie}/{nodeId}/color`. Набор строк
сохраняется одним
`PATCH /api/naryady/{id}/{zadanie|vipolnenie}/colors` с телом
`{ "color": number, "nodeIds": number[] }`. `0` сбрасывает цвет. Пустой список,
пустой идентификатор или неверный цвет дают `400`. Если хотя бы одна строка не
принадлежит этой части наряда, пакет не записывается и сервер отвечает `404`.
Закрытая часть отвечает `409`.

После успешного сохранения новый фон применяется локально ко всем строкам
набора. Синяя подсветка гаснет, чтобы был виден сохранённый цвет, но набор
остаётся: кнопки цвета активны, и цвет можно сменить без повторного выбора.
Параметры и алгоритм при нескольких строках остаются пустыми. Дерево не
перезагружается и раскрытые узлы не сворачиваются. Ошибка сохраняет выбор и
прежний фон всех строк снимка и показывает предупреждение.

## 6. Удаление работ

На панели задания и выполнения две кнопки, обе гаснут у закрытой части и на время запроса.

«Удалить помеченные работы» повторяет `actDelSelOpers`. Она активна при одной выбранной строке и при нескольких. Текст подтверждения: «Отмеченные работы будут удалены, Вы уверены, что хотите продолжить?». Сервер вызывает `burnar.zadanie_operac_del` или `burnar.vipolnenie_operac_del`. Удаление строки снимает и вложенные работы (`ON DELETE CASCADE`). Сначала обрабатываются более глубокие выбранные строки, внутри уровня — больший `prnum`. Если родитель из набора уже удалён и потомок исчез вместе с ним, повторный вызов не делается. Каждый успешный вызов фиксируется отдельно: ошибка одной строки не откатывает уже удалённые, текст процедуры показывается, дерево перечитывается. Успех без отдельного сообщения.

В выполнении, если среди выбранных есть `locked = 1`, удаление не начинается. Сообщение: «Не допускается удаление заблокированных работ!», выделение снимается. В задании блокировка удаление не останавливает. Родитель со структурой (`operlifetype = 81`) получает отказ процедуры «Нельзя удалять работы из структуры!».

«Удаление блока без удаления входящих работ» повторяет `actZadanie_del_block` / `actVipolnenie_del_block` и вызывает `*_operac_del_block`. Кнопка активна, только когда выбрана ровно одна строка и это незаблокированный несистемный блок (`operlifetype` пустой, `RS = 0`): у таблицы нет отдельной «текущей» строки помимо набора. Подтверждение: «Удаление блока приведет к переносу внутренних работ на его уровень!» и «Вы уверены, что хотите продолжить?». Системный блок (`razdel` 13555–13566) получает «Невозможно удалить основной блок!». Поля для кнопки читаются `GET .../{zadanie|vipolnenie}/nodes/{nodeId}/action`, когда выбрана одна строка.

Кнопка «Удалить» на списке нарядов по-прежнему без обработчика.

Пока `resetSelectionSignal` не перенесён в пакет `mainComponent` из `mainComponent-changes/BaseTable/BaseTreeTable.tsx`, после удаления синяя подсветка в дереве может остаться до следующего обычного клика. Набор для футера и кнопок при этом уже пустой.

## 7. Сквозные параметры

Повторяет `formSkvZadVar` / `formSkvVipVar` (`actOpenSkvZad` / `actOpenSkvVip`, `Ctrl+Y`).
Кнопка «Сквозные параметры задания» / «Сквозные параметры выполнения» стоит первой на панели
своей вкладки и доступна всегда, как в Delphi. Заголовок окна: «Сквозные параметры задания
(план): {название}» / «Сквозные параметры выполнения (факт): {название}».

Окно — `DraggableDialog` с `modeless`: без своей подложки и ловушки фокуса, клики принимает
только само окно. Карточку закрывает одна общая подложка (`SkvParamsWindows`), поэтому
с открытыми окнами задания и выполнения можно работать одновременно. Нажатие поднимает окно
наверх. Окна стоят ниже уровня `modal`, чтобы подтверждения, меню списка и календарь
были поверх них. В заголовке окна задания иконка открывает рядом окно выполнения
(только если `defnarvip` есть; подсказка — «Сквозные параметры выполнения»), в окне выполнения —
окно задания. Новое окно встаёт справа
от открытого, если помещается, иначе слева.

| Поле | Источник | Правка |
|------|----------|--------|
| Дата и время начала работ | `defnar{zad,vip}.begdate`, до минут | обязательна; часы 0–23 и каждая минута, колонки без полосы и без пустого хвоста прокрутки |
| Дата закрытия от изменений | `closeddate` (ставит `trg_defnar*_upd` при `closed = 1`) | только чтение |
| Закрыто от изменений | `closed` | только чтение |
| Параметр | `public.getparnm(parcode)` | — |
| Значение | `znval` → `common_spr.nm`; список — поддерево `common_spr` под `parcode` (как `HIERARCHY1`) | выпадающий список |
| Числовое | `val`, `numeric(8,4)` | ввод как `EdKeyPress`: цифры, одна запятая, ведущий минус |
| Строковое | `valstr`, до 150 символов | ввод |

Только чтение: задание закрыто; выполнение закрыто или в нём есть работа с `locked = 1`
(`lLocked`). Причина — во всплывающей подсказке значка справа от «Закрыто от изменений».
Пока значение отличается от исходного, название параметра и текст этой ячейки жирные.
Длинный текст в ячейках переносится на следующую строку, а не обрезается точками.
Ширины колонок таблицы общие для всех нарядов и свои у задания и выполнения
(`naryad-column-sizing:skv-zadanie` / `:skv-vipolnenie`).

«Сохранить» активна, когда есть изменения, дата задана и числа введены верно. Если менялись
«Значение» или «Числовое», сначала вопрос Delphi «Внимание! Вы изменили сквозные параметры
наряда…». Только «Строковое» вопроса не требует: `*_set_skvparam` его не получает.
`PUT /api/naryady/{id}/{zadanie|vipolnenie}/skv` с `{ begDate, params }` одной транзакцией:

1. описатель читается `FOR UPDATE`, закрытие и блокировка проверяются заново (`409`);
2. `UPDATE zndefnar*atrib` только по реально изменённым строкам (`defnar + parcode + prnum`).
   Триггер `trg_zndefnar*atrib_upd_after` → `burnar.{zadanie,vipolnenie}_set_skvparam`
   пишет новое значение в параметры работ (`*_param.znach` по `common_spr.normparorzn`),
   обнуляет их нормы и удаляет источники (`*_ist`). `trg_log_atrib_*` пишет `log_atrib`;
3. если дата изменилась — `UPDATE begdate` (`trg_defnar*_upd` пишет `log_nar`)
   и `CALL burnar.*_set_date(narkey)`: время начала работ по порядку дерева с шагом нормы.

Отказ любого шага откатывает всё, текст показывается диалогом. Успех — «Изменения успешно
сохранены!», окно перечитывает шапку и таблицу, дерево и параметры строки своей части
перечитываются. «Отмена», крестик и `Esc` при несохранённых правках спрашивают
«Изменения не сохранены. Закрыть?».

`GET .../skv` — шапка `{ begDate, closed, closedDate, readOnly, readOnlyReason }`.
`GET .../skv/params` — строки для `BaseTable` и сразу пункты `values: [{ id, nm }]`
всех параметров одним обходом `common_spr`. Сохранённое значение вне поддерева
дописывается в свой список.

Таблица — `BaseTable` пакета без изменений: редакторы рисуются в `columnDef.cell`, правки
лежат в черновике окна (`SkvEditorContext`), а не в данных таблицы. Список значений —
MUI `Select` по полю `values` строки, без отдельного запроса на параметр.

Известная ошибка в базе: в `burnar.vipolnenie_set_skvparam` условие
`and p.parcode=rec.parcode` ссылается на псевдоним `p`, которого нет в `UPDATE`. Пока
его не исправят на `and parcode=rec.parcode`, сохранение параметра выполнения с
`normparorzn` падает, и транзакция откатывается целиком.

## 8. Расчёт операции и параметры строки

Кнопка «Расчёт нормы» (`actCalcOperAndSaveRes`, `Ctrl+B`) стоит на панели задания и выполнения
перед блокировкой: у задания — после закрытия и перед цветом, у выполнения — перед
«Блокировать текущую работу». Активна, когда выбрана одна работа без вложенных, часть открыта,
работа не заблокирована и `operlifetype` равен 79 или 80. Тип 82 в Delphi кнопку не гасит, но
обработчик для него ничего не делает; в вебе кнопка для него выключена. Ручной ввод нормы
(`cbNormEdit`) для типа 82 по-прежнему не перенесён.

`POST /api/naryady/{id}/{zadanie|vipolnenie}/{nodeId}/calc` одной транзакцией:

1. описатель и строка читаются `FOR UPDATE`; закрытие, блокировка, вложенные работы и чужой тип
   дают `409`;
2. `izmer` берётся из `sprnartype` по `defnar.nartype`;
3. `CALL burnar.{zadanie|vipolnenie}_rebuild_oper`. Если `aisrebuild = 1`, ответ
   `{ rebuilt: true }`, клиент показывает «Операция была перестроена проверьте параметры и
   повторите рассчет!» и перечитывает дерево, параметры и алгоритм;
4. иначе `*_calc_operp`, затем `SetNextDateOper{ZAD|VIP}`. Новые даты читаются из
   `burnar.tkeydate` по `userenv.os_user` и сразу удаляются.

Успешный расчёт ничего не сообщает. Норма на единицу, норма на объём, источник и интервал
пишутся в выбранную строку, время начала — в строки из `tkeydate`. Дерево не перечитывается,
раскрытые узлы не сворачиваются. Пустой OUT-параметр ячейку не затирает, как в Delphi.
Итоги внизу перечитываются.

Параметр строки сохраняется сразу, без отдельной кнопки (`cbParValuesExit`).
`GET .../params` для типа 79/80 отдаёт `ptype`, `editable`, `nodeId` и у дискретного параметра
`values: [{ id, nm }]` одним запросом `qrAllZnTekDiscrParam`. Сохранённый код вне этого списка
дописывается в свой список. `ptype` 1 — поле ввода (цифры, одна запятая, ведущий минус),
`ptype` 2 — выпадающий список, первым пунктом пустое значение.

`PUT .../params/{nodeId}/{parcode}` с `{ value }` (`null` очищает):

1. часть не закрыта; в выполнении работа не заблокирована (в задании блокировка ячейку не
   закрывает, как `ReadOpParams`);
2. непрерывное значение округляется до `numeric(16,4)`, дискретный код должен быть в списке;
3. если значение не изменилось, нормы не трогаются;
4. иначе `UPDATE *_param`, `UPDATE *_norm SET norma = NULL`, `DELETE FROM *_ist`.

В строке дерева после этого пустеют обе нормы и источник, итоги перечитываются, таблица
параметров запрашивается снова (мог смениться признак сквозного). Пока ячейка не потеряла фокус,
расчёт ждёт это сохранение: оба действия стоят в одной очереди.

В Delphi клик по строке закрытого выполнения снова включает таблицу параметров, если работа не
заблокирована (`ReadOpParams` затирает `GrdParams.Enabled`). В вебе закрытая часть остаётся
только для чтения.

Отказ процедуры или проверки показывается диалогом, уже записанное в этой транзакции откатывается.

### Факт и корреляция — когда появится ввод факта

Сейчас расчёт выполнения не трогает факт. В Delphi после `VIPOLNENIE_CALC_OPERP`, если ячейка
«Факт» заполнена, вызывается `trGrdNarCellValChange`: по `burnar.factkorr` (`idlife = operlifeid`)
форма сама считает новые факт и норму на объём скриптом `TPasCalc` (поля `fact` и `norma`) и
пишет их в `vipolnenie_norm` через `SaveNormaAndFact` (значения делятся на `kf`). Если строки
`factkorr` нет, в базу уходит только факт.

Когда в вебе появится ввод факта, этот шаг нужно вызвать и после расчёта выполнения, и из самого
ввода: прочитать `factkorr`, посчитать факт и норму, записать `vipolnenie_norm` для `prnum` 1 и 2
и обновить итог факта. Пока факта в карточке нет, после расчёта остаётся прежний факт, а норма
берётся из `vipolnenie_calc_operp`.

## 9. Устройство кода карточки

Карточка лежит в `frontend/src/features/naryad/`. Список нарядов (`pages/Home.jsx`) и каталог (`pages/CatalogDialog.jsx`) остаются в `pages/`.

Вкладка задания и вкладка выполнения — один компонент `NaryadWorkspacePanel` с разным описанием части (`parts/zadaniePart.js`, `parts/vipolneniePart.js`). В описании всё, чем части отличаются: url, колонки, ключи `localStorage`, флаг `features.locks` и список кнопок `actions` в порядке показа. Проверок `part === 'vipolnenie'` в общем коде нет.

`useNaryadWorkspaceState` собирает состояние вкладки: выбор и сигналы дерева (`useWorkTree`), общую блокировку «идёт запрос» (`useMutationRunner`), итоги, признаки блокировки, поля строки и алгоритм (`useWorkspaceData`), цвет (`useRowColorEditing`). Результат лежит в `NaryadWorkspaceProvider`, кнопки читают его через `useNaryadWorkspace()`. Контекст свой у каждой вкладки: обе живут одновременно и не видят выбор друг друга.

Одна кнопка Delphi (`TAction`) — один модуль в `actions/<тема>/`:

```js
export const deleteBlockAction = {
  id: 'delete-block',
  label: 'Удаление блока без удаления входящих работ', // или getLabel(ctx)
  icon: FolderDelete,                                  // или getIcon(ctx)
  isEnabled: (ctx) => canDeleteBlock(...),             // аналог ActionList1Update
  async run(ctx) { ... },
}
```

Если у действия свой интерфейс (палитра, диалог ввода), модуль отдаёт `{ id, Component }`, и компонент сам берёт контекст. Правила доступности и тексты сообщений — чистые функции в `*Rules.js` рядом, с тестами на `node:test`. Обработчик, который продолжает работу после `await` (подтверждение, запрос), читает выбор и флаг закрытия через `ctx.tree.getSelectedIds()` / `ctx.getClosed()`, а не из замыкания. Изменения идут через `ctx.runMutation(work, { reload })`: пока запрос в полёте, остальные кнопки и очередь цвета ждут.

Новое действие: модуль в `actions/`, правила и тест рядом, строка в `actions` нужных частей. Если действию нужны данные с сервера, хук загрузки добавляется в `useWorkspaceData.js` и в контекст.
